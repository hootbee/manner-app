# 0010. 도전과제: 일일·주간·업적을 기록에서 계산한다

상태: 채택
날짜: 2026-11-18 (같은 날 열린 질문의 사용자 답 반영)

## 배경
2026-11-18 사용자 결정: 도전과제 탭(일일·주간·업적)을 MVP에 넣는다. 화면은 PR #67의 `app/lib/screens/challenges_screen.dart`에 있고, 고정 문구만 그리며 데이터 연결은 없다. "보상 받기" 버튼은 없다.

화면을 `Backend`에 연결하려면 미션마다 "무엇을 몇 개 하면 달성인가"가 기록으로 계산되는 규칙이어야 한다. 기존 결정 세 곳과 겹친다.
- 칭호는 MVP에서 뺐다(ADR 0002 §2). 기획서는 칭호를 "스탯과 스킬 조합으로 정하는 이름"으로, 배지를 "유지하는 것"으로 따로 적는다(`docs/concept.md` 89~90행).
- 주간 보상은 뺐다(`docs/decisions.md` 트랙, ADR 0002 열린 질문).
- 카테고리 기준이 없었다. 이 ADR의 열린 질문에 대한 답으로 #64의 6개로 정했다(이슈 #28).

원칙은 "언제나 단순한 시스템"이다(ADR 0004). 새 테이블과 예외 규칙 없이, 기록 집합 + 콘텐츠 + 오늘 날짜로 계산한다.

## 결정
### 1. 한 줄 규칙
**미션 = 지표 하나 × 기간 하나 × 목표 수.** 지금 값이 목표 이상이면 달성이다. 보상(XP, 코인, 아이템)은 없고 진행만 보여 준다. 아무것도 저장하지 않는다.

- 일일 탭의 기간은 오늘, 주간 탭은 이번 주, 업적 탭은 전체다. 같은 지표를 기간만 바꿔 쓴다. 그래서 "매너 탐험가(주간)"와 "탐험가(업적)", "복습하는 습관(주간)"과 "복습 습관(업적)"은 같은 지표를 이번 주와 전체로 센 것이다. 합치지 않는다.
- 모든 지표는 추가 전용 기록의 개수다. 기록이 지워지지 않으므로 업적은 한번 달성하면 계속 달성이다(예외는 결과 절 "콘텐츠 업데이트").
- 도전과제는 카테고리 축만 쓴다. 영역 6개는 스테이터스 육각형에만 쓴다. 한 기능 안에 축이 하나면 지표가 하나 줄고, 탐험가와 마스터가 같은 6개를 가리키며, 화면 문구("여러 카테고리의 매너를 배워요")와도 맞는다.

### 2. 기간과 날짜 경계
- 날짜는 기록에 있는 기기 날짜(`solved_on`, `completed_on`)의 연월일만 쓴다. 엔진의 `day()`와 연속 학습일 계산과 같은 기준이다(ADR 0004 §1). 오늘은 `live/`가 기기 시계로 넘긴다.
- **오늘**: 날짜 = 오늘.
- **이번 주**: 월요일에 시작한다. 날짜의 주 시작(`weekStart`)이 오늘의 주 시작과 같으면 이번 주다. 기기 시계가 앞서 오늘보다 늦은 같은 주 날짜도 이번 주로 센다(연속 학습일처럼 따로 막지 않는다).
- **전체**: 모든 기록.

```dart
// engine/challenges.dart. DateTime.weekday는 월요일 1 ~ 일요일 7
DateTime weekStart(DateTime t) { final d = day(t); return DateTime.utc(d.year, d.month, d.day - (d.weekday - 1)); }
```

### 3. 카테고리를 콘텐츠에 붙이는 법
**기본 시나리오의 `tags`에 카테고리 id를 하나 넣는다.** id는 `transport`, `public`, `dining`, `conversation`, `school-work`, `digital`이다(ADR 0003 §1 `key` 형식, #64 `app/assets/` 폴더 이름과 같음). 목록은 `lib/content/content.dart`의 상수 `categories` 하나에 두고, 엔진과 검사기가 함께 쓴다.

- 축 보기는 `tags`를 덮어쓸 수 없으므로(ADR 0003 §3) 펼친 문제는 모두 기본 시나리오의 카테고리를 따른다.
- 검사(ADR 0003 §6에 더함): `tags`에 카테고리 id가 둘 이상이면 오류, 출제 가능한 시나리오에 카테고리 id가 없으면 경고.
- 첫 출시 전이므로 `schema: 1` 안에서 `tags`에 뜻을 붙인다(ADR 0003 §4).

### 4. 지표 (기록에서 세는 것 6가지)
| 지표 | 세는 것 | 콘텐츠에서 못 찾은 기록 |
| --- | --- | --- |
| 풀이 수 | 기간 안 `attempts` 개수. 다시 풀기와 중간에 나간 세트도 센다(XP와 같다) | 센다 |
| 데일리 마친 날 | 기간 안 `completed_on`의 서로 다른 날짜 수(기기 두 대가 같은 날 마쳐도 하루) | 센다(연속 학습일과 같다) |
| 서로 다른 매너 | 기간 안 기록의 매너 수(`Content.lookup`의 `manner`) | 기본 시나리오로 매너를 찾으면 센다. 둘 다 없으면 뺀다 |
| 서로 다른 카테고리 | 기간 안 기록의 펼친 문제 카테고리 수(최대 6) | 펼친 문제를 못 찾으면 뺀다 |
| 최선 풀이 수 | 기간 안 `grade = best`인 풀이 중, 펼친 문제가 조건(위치 형식 `format = position`, 순서 형식 `format = order`, 또는 카테고리)에 맞는 것의 수 | 뺀다 |
| 다시 푼 매너 | (매너, 날짜) 쌍 중 그 매너를 그보다 앞선 날짜에도 푼 쌍의 수. 날짜가 기간 안인 쌍만 센다. 앞선 날짜는 기간 밖이어도 된다 | 매너를 못 찾으면 뺀다 |

- 은퇴한 매너·문제의 기록도 센다. 지난 기록은 은퇴한 항목으로도 찾는다(ADR 0003 §2). 영역 스탯과 달리 "지금 실력"이 아니라 "한 일"을 세기 때문이다.
- 카테고리와 형식은 펼친 문제를 찾은 기록에서만 읽는다. 콘텐츠에 없는 id를 `~` 앞으로 쪼개는 것은 매너를 찾을 때뿐이다(ADR 0003 §1).
- "다시 푼 매너"는 Leitner 복습일과 상관없다. 홈의 "복습 N개"(복습일 기준, ADR 0004 §2)와 뜻이 다르지만, 복습일을 날짜마다 다시 계산하지 않아도 되고 "배운 매너를 다시 떠올려요"라는 화면 설명과 맞는다. 데일리 세트의 복습 자리(ADR 0004 §4)에 나온 매너는 모두 여기에 들어간다.

### 5. 미션 (2026-11-18 사용자 확정)

- 카테고리 마스터 6개는 `categories` 순서대로 놓는다. 이름은 대중교통·공공장소·식사·대화·학교·직장·디지털 마스터다.
- 업적 목표는 콘텐츠 크기에 묶지 않고 고정 수로 둔다. "모든 매너"로 두면 매너가 늘 때 이미 단 배지가 사라진다.
- 일일 탭의 세 미션은 데일리 하나를 마치면 모두 달성된다. 데일리 6문제의 절반이 3이다(`docs/decisions.md` 트랙).

**PR #67에서 뺀 것** (2026-11-18 사용자)
| 화면 제목 | 뺀 이유 |
| --- | --- |
| 일일 "다시 한번!" | 첫날, 그리고 전날 모두 최선으로 풀어 오늘 복습 자리가 빈 날에는 데일리를 다 해도 달성할 수 없다. 데일리 세트가 복습 자리를 이미 채우므로 "오늘의 매너 완주"가 복습을 포함한다 |
| 주간 "행동으로 실천하기", "순서의 달인" | 데일리만 있으면 사용자가 문제 형식을 고를 수 없어, 이번 주 경로에 그 형식이 없으면 매일 해도 달성하지 못한다. 업적(기간 전체)은 콘텐츠가 늘면 언젠가 닿으므로 남긴다 |

### 6. 엔진 (`engine/challenges.dart`, 순수 Dart)
```dart
typedef Row = ({String id, String? category, int value, int goal}); // value는 min(지표, goal). category는 categoryMaster만(카테고리 id)

/// 목록은 5절 표 순서. 목표 수는 이 파일의 상수 하나에 둔다.
({List<Row> daily, List<Row> weekly, List<Row> achievements, int todayXp, int weekXp}) challenges(
    Content c, Iterable<Attempt> attempts, Iterable<DayCompletion> done, DateTime today);
```
- 기록을 한 번 훑어 기간별 지표를 센다. 기록이 수만 개여도 홈 계산과 같은 크기의 일이다(ADR 0004 결과).
- `todayXp`, `weekXp`는 그 기간 `attempts`의 XP 합이다(`xp()`를 기간으로 거른 기록에 부른다).

### 7. 화면 인터페이스 (`backend.dart`에 더하는 것)
```dart
abstract interface class Backend {
  // ...기존 그대로
  ValueListenable<Challenges> get challenges; // 도전과제 탭(ADR 0010)
}

class Challenges { final List<Mission> daily, weekly, achievements; final int todayXp, weekXp; } // 목록은 ADR 0010 §5 순서
class Mission { final MissionId id; final String? category; final int value, goal; } // value == goal이면 달성. category는 categoryMaster만(카테고리 id)
enum MissionId { todayStart, todayHalf, todayDone, weekDays, weekManners, weekCategories, weekReviews,
  firstStep, collector, steady, explorer, positionBest, orderBest, reviews, categoryMaster, allCategories }
```
- 제목, 설명, 아이콘은 화면이 `MissionId`로 `switch`해서 정한다. 빠진 id가 있으면 컴파일 오류가 난다. 카테고리 마스터의 이름과 아이콘은 화면이 카테고리 id로 정한다(#64의 그림 파일이 이미 id 이름이다). "N / M 달성"과 "획득한 배지 N"은 화면이 `value == goal`인 것을 센다.
- `live/`는 `_refresh()`에서 `home`, `stats`와 함께 다시 계산해 내보낸다. `engine`의 `Row.id`를 `MissionId.values.byName`으로 옮기기만 한다.
- `LoggedBackend`는 다른 값 읽기처럼 기록 없이 넘긴다(ADR 0007 §4).

### 8. 가짜 구현 (`fake/`)
`fake/`는 `engine/`을 import하지 못한다(ADR 0002 §1). 그래서 홈의 `streak`처럼 세트 진행에 따라 바뀌는 값만 같은 규칙으로 바꾸고 나머지는 고정값이다.
- 일일: `answer()`마다 풀이 수 +1(다시 풀기 포함), 마지막 `next()`에서 `todayDone` 1. `todayXp`, `weekXp`는 답의 XP(10·5·0)만큼 는다.
- 주간과 업적: `samples.dart`의 고정 목록(일부 달성, 일부 진행 중, 하나는 0)을 쓴다. `doneToday` 프리셋은 일일 셋이 모두 달성인 값으로 시작한다.

### 9. 기존 결정과의 관계
- **칭호와 다르다**: 업적 배지는 "한 일의 개수"로 정해지는 고정 목록이다. 칭호(스탯·스킬 조합으로 정하는 이름, 공유 카드)는 그대로 MVP 이후다.
- **주간 보상과 다르다**: 주간 탭은 보상 없는 진행 표시다. 주간 보상(옷장 아이템 등, 견본의 `weekly`)은 그대로 없다.
- **영역과 카테고리는 다른 축이다**: 영역 6개(연애·친구·어른·가족·직장·공공장소·메시지)는 펼친 문제의 `area`이고 스테이터스 육각형에 쓴다. 카테고리 6개는 기본 시나리오의 `tags`이고 도전과제와 카테고리별 연습에 쓴다.

## 고려한 대안
- **달성 기록 테이블(`achievements_unlocked`)**: 달성 날짜를 보여 줄 수 있다. 대신 동기화할 테이블과 RLS, 기기 두 대가 같은 업적을 각자 쓰는 경우, 탈퇴 삭제 범위가 늘고, 계산값을 저장하는 것이 된다. 지표를 모두 개수로 고르면 필요 없다.
- **탐험가는 영역, 마스터는 카테고리**: 카테고리를 붙이기 전에도 탐험가는 계산된다. 대신 도전과제 한 기능 안에 축이 둘이 되어, 탐험가 6과 마스터 6이 서로 다른 6개를 가리킨다.
- **달성하면 XP를 준다**: XP는 "모든 풀이의 점수 합"이다(`docs/decisions.md`). 보상 XP를 넣으면 XP가 기록만으로 계산되지 않거나, 보상 기록 테이블이 필요하다.

## 결과
- **쉬워지는 것**: 새 테이블, 마이그레이션, 동기화 변경이 없다. 규칙은 5절 표 한 장이고, 테스트는 기록 목록과 날짜만 만들면 된다. 목표 수를 바꿔도 지난 기록으로 바로 다시 계산된다. 카테고리별 연습이 같은 `tags`를 쓴다.
- **어려워지는 것**: 화면에 값이 하나 늘어서 `backend.dart`, `fake/`, `live/`, `LoggedBackend` 네 곳을 고친다(ADR 0002 결과). 달성한 날짜와 "방금 달성" 알림은 보여 줄 수 없다. 모든 시나리오에 카테고리를 붙이는 콘텐츠 작업이 생긴다.
- **확인할 점**
  - 네트워크 없음: 로컬 기록과 콘텐츠만 쓴다. 게스트도 같다.
  - 같은 요청 두 번: `answer()`는 `Asking`에서만 받고, 로컬 저장소는 같은 id를 무시한다(ADR 0005). 지표는 기록 개수라 두 번 세지 않는다.
  - 기기 두 대: pull 뒤 `_refresh()`가 다시 계산한다. 다른 기기의 기록이 들어오면 값은 늘기만 한다. 같은 날 두 기기에서 데일리를 마쳐도 "데일리 마친 날"은 하루다. 자정·월요일을 넘겨 켜 둔 앱은 앞으로 올 때 sync 뒤 다시 계산된다(ADR 0002 결과).
  - 탈퇴·로그아웃: 로컬 기록이 지워지면 모든 미션이 0으로 돌아간다. 따로 지울 것이 없다. 로그아웃 뒤 다시 로그인하면 pull로 돌아온다.
  - **카테고리를 붙이기 전**: 지금 `app/assets/content.json`에는 카테고리 태그가 없다. 붙이기 전까지 매너 탐험가, 탐험가, 카테고리 마스터 6개, 매너스 마스터는 0이다. 붙이면 지난 기록으로 바로 다시 계산된다. 출시 전에 모든 출제 가능한 시나리오에 붙여야 한다(3절 경고).
  - 콘텐츠 업데이트: 시나리오의 카테고리를 바꾸면 지표가 옮겨 가서 이미 단 카테고리 마스터가 사라질 수 있다. 바꿔야 하면 새 시나리오를 만들고 옛것을 은퇴시킨다(ADR 0003 §1과 같은 방식). 기록 id가 콘텐츠에 없는 기기(받기 전)는 카테고리·형식 지표가 잠시 작다.
  - 콘텐츠 크기: 지금 순서 문제가 0개이고 매너가 3개라 순서 고수와 매너 수집가(30)는 콘텐츠가 늘어야 닿는다.
- **넣지 않은 것과 넣을 시점**
  - 달성 날짜, 달성 순간 알림: 사용자 테스트에서 요청이 나오면 `Finished`에 "이번 세트로 새로 달성한 미션"을 더한다(세트 전후 `challenges()` 비교, 저장 없음).
  - 분석 이벤트: 넣지 않는다(ADR 0006은 이벤트를 최소로 둔다). 도전과제가 학습을 늘리는지 봐야 할 때 탭 열기 이벤트 하나를 더한다.
- **다시 볼 조건**: 카테고리별 연습을 넣을 때(사용자가 형식을 고를 수 있게 되면 주간 형식 미션을 되살릴지), 목표 수가 너무 쉽거나 어렵다는 의견이 나올 때(상수만 바꾼다).

## 다른 문서에 미치는 영향 (고칠지는 사용자가 정한다)
1. ADR 0002 §2 인터페이스 코드: `challenges` 게터와 `Challenges`, `Mission`, `MissionId`를 더한다(7절). 45행 "카테고리 연습: 기준이 정해지면 `startPractice(String categoryId)`"는 이제 기준이 정해졌다.
2. ADR 0002 §2 94행 "MVP에서 빼는 것: … 칭호": 그대로 맞다. 헷갈리지 않게 "도전과제 배지는 칭호가 아니다(ADR 0010)"를 덧붙일 수 있다.
3. ADR 0002 §3 99~100행: `FakeBackend` 생성자와 프리셋 설명에 도전과제 고정값을 더한다(8절).
4. ADR 0002 결과 138행 "다시 볼 조건": 도전과제를 더했다는 것을 적을 수 있다. 156행 "주간 보상은 뺀다"는 그대로 맞다.
5. ADR 0001 §4 94행 "진행 위치와 주간 보상": 주간 보상은 이미 뺐으므로 "진행 위치와 도전과제"로 바꾼다.
6. ADR 0003 §3 41행 `tags` "카테고리 기준이 정해지면 쓴다. 지금은 뜻을 정하지 않고, 앱도 읽지 않는다": 3절로 뜻이 생겼다. §6 검사표에 3절의 오류·경고 두 줄을 더한다.
7. ADR 0004 결과 137행 "카테고리 연습 출제: 카테고리 기준이 정해지면": 기준이 정해졌다.
8. `docs/concept.md` 67행 "카테고리 기준은 추후 결정한다", 69행 "문제마다 카테고리 태그": 6개로 정해졌고 태그는 문제가 아니라 기본 시나리오에 붙는다. 188~196행 MVP 화면 목록에 도전과제가 없다.
